# 프롬프트 3기법 비교 리포트

## 1. 과업 정의
- 선택 과업 : 고객 문의 분류 및 긴급도 판정
- 분류 카테고리 : `주문`, `배송`, `환불`, `제품문의`, `기타`
- 긴급도 판정 기준 (1~3):
  - `3 (높음)`: 당일/즉각 조치 필요, 금전 피해, 오배송 긴급 수거, 출고 직전 정보 변경, 강한 클레임
  - `2 (보통)`: 일반 주문/배송 현황 조회, 단순 반품/교환 절차 문의, 일반 작동법 질문
  - `1 (낮음)`: 단순 스펙/정보 확인, 단순 규정 문의, 사후 의견
- 출력 형식: `{"type": "...", "urgency": 1~3}`

## 4. 결과 표 (15회)

> **형식 준수(O/X) 판정 기준**: 프로그램이 응답 전체(Zero/Few-shot) 또는 약속한 마지막 줄(CoT)을 `json.loads()`로 읽을 수 있는가?
> - Zero-shot: 5줄로 개행된 JSON 문자열이 반환되어 개별 파싱 시 형식 O[cite: 2].
> - Few-shot: 단일 JSON 배열(`[...]`) 형태로 묶여 반환되어 한 번에 파싱 가능하므로 형식 O[cite: 6].
> - CoT: 각 문의 블록별 마지막 줄만 추출하면 유효한 JSON이므로 형식 O[cite: 3, 4].

## 6. 분석

- **형식 준수**:
  - 세 기법 모두 마크다운 코드 블록(\`\`\`json)을 쓰지 말라는 지침을 준수하여 파싱 가능한 텍스트를 출력함[cite: 2, 3, 4, 6, 7, 8, 9, 10].
  - **Zero-shot**: 문장별 JSON을 개행으로 분리해 반환하여 개별 줄 단위 파싱이 필요함[cite: 2].
  - **Few-shot**: 여러 입력을 배열(`[...]`) 형태로 스스로 감싸 반환하여 `json.loads()` 한 번으로 안정적인 일괄 파싱이 가능했음[cite: 6].
  - **CoT**: 추론 텍스트가 앞에 배치되므로 전체 문자열을 바로 파싱하면 에러가 발생함[cite: 3, 4]. 다만 프롬프트 약속대로 각 블록의 "마지막 줄"에만 JSON이 위치하므로 슬라이싱 로직을 거치면 문제없이 파싱 가능함[cite: 3, 4].
- **분류 정확성**:
  - 명확한 사례(1~3번)는 세 기법 모두 의도를 정확히 파악함[cite: 2, 3, 4, 6].
  - 가장 애매했던 **5번 사례(성분 불만 및 병원비 청구)**에서 기법 간 차이가 극명하게 드러남:
    - Zero-shot과 Few-shot은 5건 일괄 처리 시 '상세페이지'라는 단어에 매몰되어 '제품문의'로 오분류함[cite: 2, 6].
    - CoT는 1단계에서 "병원비 청구 접수 목적", 2단계에서 "신체 및 금전 피해 발생"을 단계별로 짚어내며 '제품문의' 함정에 빠지지 않고 정확한 의도를 짚어냄[cite: 4, 7, 8].
- **일관성**:
  - 5번 단독 반복 실행 시, CoT는 3회 연속 1·2단계의 동일한 추론 구조를 유지하며 `{"type": "환불", "urgency": 3}`이라는 일관된 결과를 출력함[cite: 7, 8].
  - Zero-shot과 Few-shot의 경우 단독 반복 실행에서는 3회 모두 '기타 / 3'으로 일관되었으나, 앞선 5건 일괄 처리(`제품문의 / 3`)와 비교했을 때 프롬프트 내 배치 환경에 따라 결과가 흔들리는 경향을 보임[cite: 2, 6, 9, 10].
- **비용 (출력 토큰)**:
  - CoT는 단계별 추론 과정으로 인해 출력 토큰 수가 Zero-shot 및 Few-shot 대비 약 3~4배 이상 많아 API 호출 비용과 응답 지연(Latency)이 큼[cite: 2, 3, 4, 6].


## 7. 결론 — 우리 팀이 쓸 기본 전략

우리 팀은 파이프라인의 기본 프롬프트 전략으로 **Few-shot**을 채택하고, 긴급 판정이 모호한 예외 건에 대해 **CoT를 보조 검증용으로 결합하는 하이브리드 전략**을 사용한다.

- **기본 전략으로 Few-shot을 채택하는 이유**:
  1. **형식 준수 및 파싱 안정성**: Few-shot은 코드 펜스나 불필요한 사족 없이 요구한 JSON 스키마를 가장 깔끔하게 모방하여 파이프라인 중단 위험이 없음[cite: 6, 9].
  2. **비용 및 지연시간 최적화**: CoT 대비 출력 토큰이 현저히 적어 대량의 문의 데이터를 실시간으로 분류할 때 API 호출 비용과 처리 속도 면에서 압도적으로 유리함.
  3. **예외 처리 보완책**: 5번과 같이 '보상 청구 / 반어법 / 피해 발생'이 복합된 애매한 케이스에서는 Zero/Few-shot의 오분류 리스크가 확인되었으므로, 해당 의심 패턴 감지 시에만 CoT로 2차 검증을 태우는 파이프라인 구조를 구축하는 것이 가장 합리적임.
